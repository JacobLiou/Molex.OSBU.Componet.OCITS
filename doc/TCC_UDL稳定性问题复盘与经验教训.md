## 1. 问题现象

产线三温测试（RT → LT -5°C → HT 55°C）过程中，循环箱（TCC）通讯间歇性失败，典型表现：

| 场景 | 现象 |
|------|------|
| 设温 | `SetTempSetpoint` 返回 UDL 软错误（缓存溢出 / 格式类），但箱体实际已开始变温 |
| 读温 | `GetCurrentTemp` 返回 `错误:通讯库写获取当前温度值! 代码:0x00120091` |
| 典型时序 | 读温 23.0°C 成功 → 设温 -5°C 成功 → 烤温 N 分钟（期间无 TCC 通讯）→ **烤温结束后首次读温失败** → 开扫前门禁弹框，LT 只能「重试 / 终止」 |
| 影响 | 低温/高温测试中断，整批产品三温流程无法闭环，影响产能 |

---

## 2. 处理过程回顾：应用层的补偿措施一层层叠加

在根因没确认之前，应用层陆续加了以下补偿逻辑（以当前代码为准）：

| 序号 | 措施 | 位置 | 本质 |
|------|------|------|------|
| 1 | 读温失败静默重试 3 次 / 500ms | `TryReadChamberTemperature` | 应对瞬时失败 |
| 2 | 读温失败三按钮（通过 / 重试 / 取消） | `TryReadChamberTemperatureWithOperatorConfirm` | 把决策交给操作员 |
| 3 | 操作员「通过」记忆（按目标温度） | `tccOperatorPassTempKeys` | 减少重复弹框 |
| 4 | LT/HT 不允许「通过继续测」，只能重试 / 终止 | `TryValidateChamberTemperatureWithConfirm` | 守住质量底线 |
| 5 | 设温失败重试 5 次 / 1s | `TrySetChamberSetpointWithOperatorConfirm` | 应对瞬时失败 |
| 6 | 设温报错后读回设定值校验 | `UDLTccCtrl.SetTempSetpoint` | 区分「真失败」和「误报错」 |
| 7 | 设温报错后 20s 内多点读温看趋势，朝目标变化就算成功 | `TryObserveChamberTrendAfterSetFail` | 用物理结果反推指令是否生效 |
| 8 | 设温最终失败仍静默继续烤温 | 同上 | 保产能 |
| 9 | TCC 调用加进程内锁 | `UDLTccCtrl.TccUdlLock` | 减轻并发导致的缓存溢出 |
| 10 | 无 TCC / 仅常温的标记文件 | `DisableTccChamberCheck.txt`、`RtOnlyTest.txt` | 现场应急旁路 |

**回头看**：上面每一条单独看都说得通，但合起来，**是用业务层的复杂度去掩盖基础设施层的缺陷**。问题没有消失，只是被挪到了更难排查的地方（比如烤温结束后才暴露）。

## 3. 根因

- **直接根因**：UDL Engine 内部的通讯处理缺陷（具体机制以 UDL 维护方结论为准：____）。
- **放大因素**：
  1. UDL Engine 进程内**单例共享**：TCC（GUID 1）和 FSTP（GUID 2）共用同一个 `deviceEngine`，`GetLastErrorMessage` 是 engine 级全局状态；应用层的锁只覆盖了 TCC，没有覆盖整个 engine。
  2. Engine 通讯异常后**没有自愈能力**，应用层也没有重连入口，一旦失效，「重试」实际上是对着同一个坏掉的句柄反复调用。
  3. 烤温期间**没有心跳通讯**，故障到烤温结束才暴露，代价最大。

## 4. 经验教训

### 4.1 架构层面：基础设施的稳定性必须由基础设施自己负责

```
┌────────────────────────────────────┐
│ 业务层  UIOperateInterleaverFinalTest │  ← 只应关心「温度到没到」
├────────────────────────────────────┤
│ 设备抽象层  IUDLTCC / UDLTccCtrl      │  ← 应负责：锁、重试、错误分类、重连
├────────────────────────────────────┤
│ 基础设施层  UDL2 Engine               │  ← 应保证：通讯正确、可恢复、可诊断
└────────────────────────────────────┘
```

- **Infra 的缺陷不应在业务层修补**。业务层每多一条「趋势判定」「静默继续」，就多一份质量风险，也多一份维护负担。
- **出现问题的那一层，就是应该修复的那一层**。上层可以做降级和兜底，但不能代替修复。
- **设备抽象层（`IUDLTCC`）是防腐层**：重试、锁、错误码分类、重连这些稳定性策略应集中在 `DeviceControl`，不应散落在 5000+ 行的业务文件里。

### 4.2 过程层面：先拿证据，再改代码

| 我们实际做的 | 更好的做法 |
|-------------|-----------|
| 看到报错就在业务层加重试 / 弹框 / 判定 | **第一时间收集底层日志**（`{exe}\UDLlog.txt` + `{exe}\Log\yyyy-MM-ddlog.txt`），按时间对齐 |
| 现象出现在业务流程里，就在业务流程里排查 | **写一个最小复现工具**：绕开业务，只循环调用 `UDL2_TCC.GetCurrentTemp / SetTempSetpoint`，模拟「长时间空闲后通讯」「与 FSTP 并发」等条件，快速判定问题在哪一层 |
| 多轮修改后才找 UDL 维护方 | **怀疑 Infra 时尽早升级给维护方**，带上复现步骤、错误码、日志片段 |
| 「我知道是底层问题」只停留在判断 | **把判断变成证据**：可复现的步骤、日志、错误码，这才是推动 Infra 修复的筹码 |

> 一个多月里，大部分时间花在「绕过问题」上，而不是「定位问题」上。  
> 如果第一周就拿到 UDLlog 并做出脱离业务的最小复现，根因确认可以大幅提前。

### 4.3 设计层面：业务层兜底要有边界

- **兜底可以有，但必须可见、可关闭、有期限**：
  - 可见：每次兜底都要写日志和 `RealtimeMsg`，不能完全静默（比如「设温失败静默继续」至少要能在报表里追溯）；
  - 可关闭：用配置或标记文件控制，Infra 修好后可以一键关掉；
  - 有期限：在代码注释里注明「临时规避 UDL 问题 #____，修复后删除」。
- **质量门禁不能妥协**：LT/HT 开扫前 ±2°C 门禁不允许「通过继续」，这个决策是正确的，应该保留。
- **用物理结果做最终校验**：「设温成功」不等于「温度到了」。正确的判据是实测温度进入容差并稳定，而不是指令返回 0。

### 4.4 Infra 健壮性要求（反馈给 UDL 维护方 / 未来选型参考）

| 要求 | 说明 |
|------|------|
| 错误可区分 | 错误码要分清「瞬时可重试」「需要重连」「设备故障」三类 |
| 可自愈 | 通讯句柄失效时 engine 内部自动重开，或提供公开的 `Reconnect` / `Close+Open` 接口 |
| 线程安全 | 明确声明是否线程安全；`GetLastErrorMessage` 应按调用或按线程隔离，而不是全局共享 |
| 长时间空闲稳定 | 空闲数十分钟后的首次通讯必须可靠（烤温场景是常态） |
| 可诊断 | 调试日志包含时间戳、端口、收发原始帧和底层系统错误码 |
| 版本可追溯 | 每次发布注明版本号、变更内容、与 `UDLConfig.xml` 的兼容性 |

> **基础设施的问题要在基础设施层解决；业务层能做的是快速定位、拿出证据、有边界地兜底，而不是长期替基础设施背锅。**
